## D-001 界面选型：Electron + Vue 3

**决策**：使用 Electron 38 + Vue 3.5 + Vite 7 + TypeScript 5.9 构建 Windows 桌面应用，
打包保留两条路线：electron-builder 出 NSIS 安装包（`npm run dist:nsis`，**受限网络下本机做不出来**，
见 D-017），以及离线手工组装的便携版（`npm run dist:portable`，**本机已实测产出并跑通**，见 D-017）。

**备选方案**

| 方案 | 优点 | 在本项目中的致命问题 |
| --- | --- | --- |
| **Tauri**（Rust + WebView2） | 体积小、内存占用低、同样是真桌面应用 | 本机 **Rust / cargo 缺失**。要先把整条 Rust 工具链装好、编译 Rust 侧依赖，三天工期里这是不可控风险 |
| **PySide6 / PyQt** | Python 写界面快，ffmpeg 调用方便 | 本机 **Python 环境已损坏（缺 `pyvenv.cfg`）**，解释器本身跑不起来，要先修环境 |
| **WPF / WinForms**（.NET） | 原生 Windows 客户端关联度最高 | 本机 **.NET SDK 缺失**，需先装 SDK |
| **Web 应用 / 命令行工具** | 最快 | 直接违反需求 6：界面选型与"客户端"关联为 0 不予考虑 |

**选择理由**

1. **需求 6 是硬约束**：评审明确要求界面选型必须与"客户端"强关联。Electron 产出的是真正的桌面应用——
   原生窗口与窗口控制、系统文件对话框、资源管理器集成（`shell.showItemInFolder`）、系统通知、可安装的 exe，
   而不是"网页 + 一个壳"。这一点在 README 的"需求 6"一节有具体举证。
2. **本机环境探测结果是决定性的**：Node 26 可用且能联网，npm 能装包，
   Electron 是四条候选路线中**唯一开箱即跑、且能在三天内产出 Windows 安装包**的原生客户端路线。
   这不是"Electron 技术更优"，而是"在给定环境下 Electron 可行，其余三条都要先解决工具链缺失"。
3. **前端生态与 ffmpeg 命令行天然契合**：Node 侧 `child_process.spawn` 调 ffmpeg 是最直接的方式，
   渲染层用 Vue 3 描述"参数 → 命令"的映射关系也很自然。

**代价 / 权衡**

- **安装包体积大**：Electron 运行时本身约 200 MB 量级，再加上 ffmpeg 61 MB + ffprobe 77 MB，
  产物远大于 Tauri。对"格式转换器"这类自带重型二进制的工具来说尚可接受，但这是实打实的代价。
- **内存占用高**：多进程模型（主进程 + 渲染进程 + GPU 进程）比原生应用吃内存。
- **仍然带一个 Chromium**：对纯粹的工具类应用而言这是"为了 UI 开发效率付出的运行时成本"。
- **打包链路更复杂**：asar、`extraResources`、原生二进制路径都要单独处理（见 D-014 与 D-017），
  这也是本次会话中最后才补齐的环节——**NSIS 安装包至今没做出来**（受限网络，原因见 D-017），
  实际交付的打包产物是离线手工组装的便携版。
- **放弃的机会**：如果本机 Rust 环境可用，Tauri 在体积与内存上明显更优。这个决策是环境约束的产物，不是技术偏好。

## D-002 状态管理：自研组合式函数而非 Pinia

**决策**：用 `renderer/composables/useStore.ts` 一个模块级单例（`ref` / `computed` + 导出函数）管理全部前端状态，
不引入 Pinia。

**备选方案**

- **Pinia**：Vue 官方推荐方案，有 devtools 支持、时间旅行调试、模块化 store。
- **Vuex**：更重，已不是首选。
- **组件内 `provide/inject`**：适合局部共享，跨页面共享时要层层透传。

**选择理由**

1. **状态图很简单**：只有 5 组状态——文件列表、任务列表、设置、能力探测结果、当前视图。
   没有嵌套模块、没有复杂的跨 store 依赖，一个模块级单例 + `ref` 就够。
2. **状态的真实归属在主进程**：任务状态由 `ConversionEngine` 持有，渲染层只是**投影**
   （收到 `job:updated` 就重绘）。这意味着"状态管理的复杂度"其实被推到了 IPC 边界之外，
   前端这层不需要 store 框架提供的那些能力。
3. **少一层抽象、少一份打包体积**：不引 Pinia 就不需要理解它的 store 定义/解构/`storeToRefs` 等约定，
   也少一个依赖的版本兼容面。

**代价 / 权衡**

- **没有 devtools 时间旅行**：调试状态变化只能靠日志/断点。对这个体量的应用影响不大。
- **HMR 行为需要自己注意**：模块级单例在 Vite HMR 下可能保留旧状态，需要手动刷新页面。
- **缺少约定的约束力**：Pinia 强制"改状态必须走 action"，自研方案里任何组件都能直接改导出的 `ref`。
  本项目靠约定（变更集中在 `useStore.ts` 导出的函数里）维持，**这是靠自觉而不是靠工具保证的**。
- **规模上限低**：如果这个应用继续长大（多窗口、插件系统、复杂撤销重做），
  自研方案会先变得难以维护，届时应迁移到 Pinia。当前是"够用且不再多"，不是"更好"。

## D-003 主进程构建：esbuild 直接打包

**决策**：写 `scripts/build-electron.mjs`，用 esbuild 把 `electron/main.ts` 与 `electron/preload.ts`
各 bundle 成单文件 CJS（`dist-electron/main.js`、`dist-electron/preload.js`）。

**备选方案**

| 方案 | 说明 | 问题 |
| --- | --- | --- |
| **vite-plugin-electron** | 与渲染层共用一套 Vite 配置，社区常用 | 引入一个额外插件与它的一整套约定；主进程代码量很小，用不上 Vite 的模块图与 HMR 能力 |
| **tsc 直接编译** | 只用 TypeScript 编译器，零额外依赖 | 产出的是保持目录结构的多个 `.js` 文件 + 需要处理模块解析；`shared/` 的引用路径在运行时容易出错；体积与启动开销都不如单文件 |
| **tsup / rollup** | 更专业的库打包工具 | 对一个 62 KB 的产物来说属于过度配置 |

**选择理由**

1. **快**：esbuild 打包主进程与 preload 合计不到 100 ms，`--watch` 模式下改代码几乎无感。
2. **产物简单**：两个单文件，`package.json` 的 `main` 直接指向 `dist-electron/main.js`，preload 路径也是固定拼接，
   没有模块解析的运行时开销与路径陷阱。
3. **`external` 极简**：只需要排除 `electron` 本身（运行时注入，不能打进 bundle），
   于是 `external` 就是 `['electron']` 一行。本项目的 ffmpeg / ffprobe **不由任何 npm 包提供**
   （见 D-004，二进制由 `scripts/fetch-binaries.mjs` 抓到 `resources/bin/`），
   所以**不需要为二进制包配置 external**，也就没有"忘记加 external 导致打包后运行时报错"这类隐患。
4. **不引入第二套构建体系**：渲染层用 Vite、主进程用 esbuild，两条链路各自独立、互不干扰，
   比"用一个插件把两件事耦合起来"更容易排查问题。

**代价 / 权衡**

- **两套构建配置**：改了 `shared/` 的代码要意识到两侧的构建/类型检查是分开的（`tsconfig.electron.json` 与 `tsconfig.json`）。
- **没有类型检查**：esbuild 只转译不做类型检查，类型正确性完全依赖单独跑 `npm run typecheck`（`tsc --noEmit`）。
  这意味着**构建成功不代表类型没问题**——这是 esbuild 路线的固有代价。
- **产物可读性差**：非 watch 模式下开了 `minify`，主进程报错时的堆栈会指向压缩后的代码。
  watch 模式下用 `sourcemap: 'inline'` 缓解，但生产构建的堆栈仍然不好读。
- **`external` 需要人工维护**：将来新增原生依赖时，忘记加进 `external` 会在打包后运行时报错，
  而且**只有在真正跑打包产物时才会暴露**（这也是打包验证不可省的原因之一）。
  当前 `external` 只有 `['electron']` 一项，维护面很小。

## D-004 ffmpeg 二进制分发方案

**决策**：**完全不使用 `ffmpeg-static` / `ffprobe-static` 这两个 npm 包** —— `dependencies` 为空对象，
二进制改由自己写的 `scripts/fetch-binaries.mjs` 抓取并落地到 `resources/bin/`。
两个二进制的来源优先级不同：

| 二进制 | 首选来源 | 回退来源 |
| --- | --- | --- |
| `ffmpeg.exe` | yt-dlp/FFmpeg-Builds 的 master 构建（经 GitHub 代理镜像 `gh-proxy.com` → `ghfast.top` → `ghproxy.net` 顺序回退，直连排最后） | npm 包 `@ffmpeg-installer/win32-x64` |
| `ffprobe.exe` | npm 包 `@ffprobe-installer/win32-x64`（该包比 ffmpeg 的 npm 包新且稳定） | FFmpeg-Builds（同上） |

脚本支持 `--force`（强制重下）/ `--source=npm`（只用 npm 包）/ `--electron`（顺带补装 Electron 运行时），
落地后打印文件大小与 sha256；`npm run setup` 会在 `npm install` 之后自动串行执行
`fetch-binaries.mjs --electron`。

**备选方案**

| 方案 | 说明 | 为什么不选 |
| --- | --- | --- |
| **`ffmpeg-static` npm 包（自带 postinstall 下载）** | 最省事，`npm i` 就能用 | 它的 postinstall 需要从 `github.com` 拉二进制，**本机实测超时不通**。安装过程会长时间卡住，在限时任务里不可接受。**最终决定完全不引入这个包**：`package.json` 的 `dependencies` 为空对象，`node_modules` 里也没有它 |
| **要求用户自己装 ffmpeg 并配 PATH** | 零分发成本 | 违反需求 7（要给人用）——评审 clone 下来跑不起来，直接失败 |
| **把二进制提交进 git 仓库** | clone 即可用，不依赖网络 | 仓库会膨胀到 290 MB+；且**单个文件 139 MB 已超过 GitHub 单文件 100 MB 的硬限制**，推不上去。`.gitignore` 已排除 `resources/bin/` 与 `.downloads/` |
| **只用 npm 包来源** | 最稳最快（tarball 走 npm 镜像） | 构建太老。`@ffmpeg-installer/win32-x64` 是 2018 年的构建，**缺 `libsvtav1`**，AV1 软编码不可用 |

**选择理由**

1. **绕开不可靠的网络路径**：把"从 github.com 拉二进制"换成"从 npm 镜像拉自带 exe 的 tarball"，
   走的是和装依赖同一条链路，可靠且**可重复执行**（已存在且 >20 MB 就跳过）。
2. **多来源回退提高一次成功率**：ffmpeg 首选新构建（功能全，含 AV1），失败自动回退到老但稳的 npm 包。
   任一条成功即可用，不会因为某一个镜像挂了就卡死。
3. **解包不捕获子进程输出**：环境里 `spawn(cmd, { stdio: 'pipe' })` 会 `EPERM`，
   所以解包用 `tar` 继承 stdio，失败再回退 `Expand-Archive`。
4. **落地位置与两种运行形态统一**：`resources/bin/` 在开发态是 `<项目根>/resources/bin/`，
   打包态是 `<安装目录>/resources/bin/`（由 `extraResources` 释放），代码里只需一套查找逻辑。

**代价 / 权衡**

- **首选来源这次成功了，但结论依赖网络环境**：本机最终落地的是 **FFmpeg-Builds master 构建**，
  两个二进制均为 `ffmpeg version N-126435-gf93cd72dde-20260906`，各约 139 MB。
  这与早期版本"三个代理镜像与直连全部失败、最终落地 2018 年的 `N-92722` 构建"的记录**相反**——
  说明这条链路的结果随网络环境波动，同一个脚本在不同时间/网络下可能拿到不同构建。
  GitHub 代理镜像本身就是第三方服务，可用性不受本项目控制。
- **npm 回退来源仍然是"功能缩水"的**：一旦回退到 `@ffmpeg-installer/win32-x64`（2018 年构建），
  `libsvtav1` 就没了，而 `presets.ts` 把 `av1` 预设映射到 `libsvtav1`，
  于是设置页会把"AV1（软编码）"标为不可用。也就是说**回退成功 ≠ 功能等价**，
  这是本决策最实际的代价。用 `node scripts/fetch-binaries.mjs --force` 可重新尝试首选来源。
- **构建版本不可控**：用户 `npm run setup` 得到的 ffmpeg 版本取决于下载时上游的最新构建，
  不同时间/网络环境可能拿到不同版本，行为可能有细微差异。文档里所有"实测"数字都绑定了
  本次核对的版本号 `N-126435-gf93cd72dde-20260906`，换构建后应重跑 `npm run smoke`。
- **`sha256` 只是打印不校验**：脚本计算并打印摘要，但没有期望值可比对（注释里的"有期望值时"目前永不成立），
  所以**下载完整性只有 `content-length` 一层校验**。
- **多来源带来分支复杂度**：来源 A 的压缩包目录层级与来源 B 不同，只能靠递归 `findFile()` 兜底查找。
- **`.downloads/` 会缓存约 190 MB**：为了可重复执行而复用已下载的归档，代价是磁盘占用。
  该目录**已被 `.gitignore` 排除**（早期版本曾漏掉）。

## D-005 ffmpeg 调用方式：spawn 参数数组

**决策**：`buildCommand()` 返回 **`string[]` 参数数组**，由 `process.ts` 用
`spawn(可执行文件, 参数数组, { windowsHide: true })` 直接执行，**不经过 shell**。
另存一份经引号转义的 `commandText` 仅供界面展示与复制。

**备选方案**

| 方案 | 问题 |
| --- | --- |
| **拼接命令行字符串 + `shell: true`** | 路径含空格或中文时会被 shell 拆词；路径里的 `&` `|` `^` `(` 等字符会被解释为 shell 语法，轻则失败重则执行意外命令；还要自己处理 Windows/POSIX 两套转义规则 |
| **`fluent-ffmpeg` 库** | 引入一个较重的依赖；它的 API 会在 ffmpeg 参数之上再加一层抽象，遇到它没覆盖的参数（`-progress`、`signalstats`、`zscale` 色调映射链）仍要 escape hatch；且需求 2 明确说"用 ffmpeg 命令行"，直接构造参数数组反而更贴合考察点 |
| **`child_process.exec`** | 同样是走 shell 的字符串拼接，有相同问题 |

**选择理由**

1. **正确性**：参数数组由操作系统直接传给子进程，不经过 shell 解析。
   源文件路径就是探测出来的原始路径（可能含空格、中文、括号、`&`），不需要任何转义就能正确传递。
2. **可测试、可展示**：`buildCommand()` 是纯函数（输入结构化选项 + 探测结果，输出参数数组），
   不依赖运行环境；界面要展示命令原文时再单独转义拼接一次即可。
3. **安全**：完全没有命令注入面。用户输入的"文件名模板"只影响输出路径，
   而输出路径是被当作一个参数元素传递的，不会变成命令的一部分。

**代价 / 权衡**

- **两条路径要各自维护**：真正的执行走数组，展示/复制走 `quoteArg()` 转义的字符串。
  后者是"给人看的"，它的转义规则是近似的（`commands.ts:130` 与 `convert.ts:556` 还各有一份转义实现），
  **存在"界面显示的引号与实际执行不一致"的可能**，但只影响观感，不影响执行正确性。
- **`convert.ts` 里的转义实现与 `commands.ts` 的 `quoteArg()` 重复**：两处规则略有差异
  （`commands.ts` 会把 `"` 和 `\` 转义，`convert.ts` 只是简单加引号）。属于应当合并的技术债。
- **失去 `fluent-ffmpeg` 的便利**：进度、错误、滤镜链辅助都要自己写（`progress.ts`、`errors.ts`、`commands.ts`）。
  这既是代价也是收益——需求 2 考察的正是"能不能自己把命令行组织对"。
- **不过 shell 意味着不能写管道/重定向**：本项目的所有需求（包括 `-progress pipe:1`）都能用 ffmpeg 自身参数表达，
  但如果将来需要 `ffmpeg | ffplay` 这类管道，就要另想办法。

## D-006 缩略图策略：智能选帧与缓存键

**决策**：默认走"智能选帧"而不是固定时间点抽帧：
先用 `blackdetect=d=0.1:pix_th=0.10` 扫描**前 60 秒**找出片头黑场区间，
在 10% / 25% / 50% / 5% 以及 2 秒处生成候选点，落在黑场内的候选点顺延到黑场结束后 0.4 秒，
再逐个抽帧并用 `signalstats` 取平均亮度 `YAVG`（低于 12 视为仍是黑帧就换下一个候选点）。
缓存键为 `SHA1(路径 | 文件大小 | 修改时间 | 目标宽度)`，**不含抽帧时间点**。

**备选方案**

- **固定时间点抽帧**（如固定取第 1 秒或 10% 处）：一次 ffmpeg 调用搞定，最快。
- **抽多帧拼 sprite 接触表（contact sheet）**：信息更丰富，但需要额外解码多帧，且列表卡片尺寸放不下。
- **用系统缩略图 API（`IThumbnailProvider` / `IShellItemImageFactory`）**：不依赖 ffmpeg，
  但只对系统认识的格式有效，且无法控制"选哪一帧"，对 MKV/WebM 等格式常常拿不到图。

**选择理由**

1. **固定时间点在实际片源上失败率很高**：片头黑场、台标黑屏、渐变淡入是极常见的开场方式，
   固定取第 1 秒或 10% 处很容易得到一张纯黑图——而需求 1 明确要求"获取到视频的缩略图显示出来"，
   显示一张黑图和没显示差别不大。
2. **候选点 + 亮度评估成本可控**：`blackdetect` 只扫前 60 秒且用 `-t 60` 限制，
   单次约 0.2-0.5 秒；抽帧用 `-ss` 放在 `-i` **之前**走关键帧快速定位，比解码到该时间点快一个数量级。
   整体约 0.5-1.5 秒，只在每个文件第一次分析时发生。
3. **缓存键不含时间点是为了避免反复重算**：同一文件只保留一张封面。
   如果键里含时间点，用户每次点开列表都要重新抽帧。
   "换个时间点重新取帧"被设计成**显式操作**（调用时传 `atSec`），此时覆盖同一张缓存即可。

**代价 / 权衡**

- **首次分析变慢**：比固定时间点方案多一次 `blackdetect` 扫描和最多 1-4 次亮度探测，
  每个文件首次分析多花约 0.5-1.5 秒。对批量导入 50 个文件是明显的等待（虽然不阻塞 UI）。
- **亮度阈值是经验值**：`YAVG < 12` 判定为"黑帧"是拍出来的阈值，
  对夜景、暗调影片可能出现"明明有内容却被判为黑帧"从而继续换候选点的情况（最终仍会返回第一次成功抽到的帧，不会失败）。
  需要说明的是：截至本文档撰写时，**"避开黑帧"这个核心行为还没有被真正验证过**——
  `npm run smoke` 里缩略图用例跑的是 `testsrc2` 彩条素材（没有黑场），
  实测数据是"冷缓存下 17 KB / 抽帧点 0.6s / 715 ms"，只能证明智能选帧链路能跑通、能出图、能命中缓存，
  不能证明它真的会跳过片头黑场。
- **缓存键不含时间点是一把双刃剑**：好处是不反复重算；
  代价是**用户手动选定的封面会被下一次智能选帧的结果覆盖**（同一个键指向同一个文件），
  且无法在同一文件上同时保留"自动封面"和"用户选定封面"两张图。
- **缓存不会自动清理**：只有设置页的手动"清理缓存"按钮。
  `mtime + size` 变化会让旧缓存失效但**不会删除旧文件**，长期使用会留下垃圾文件。
  （`clearThumbnailCache()` 会返回释放的字节数，说明作者意识到了这个问题，但没有做容量上限与 LRU。）
- **抽帧失败判据是启发式的**：小于 512 字节视为空图，这是个便宜的近似。
- **`probe.ts` 里另算了一份 `thumbnailAtSec`**（`clampThumbnailTime()`：时长的 10%、下限 1 秒、上限 30 秒），
  但缩略图模块**并不使用它**——`getThumbnail()` 在智能模式下自己按 10%/25%/50%/5% + 2 秒另算候选点。
  全仓库唯一读取 `thumbnailAtSec` 的地方是 `scripts/smoke-test.mjs` 的一条断言，
  **产品代码不消费这个字段**。两处逻辑重叠，属于该合并的遗留（详见 `SESSION_SUMMARY.md` 第 5.2 节第 10 条）。
- **避黑场能力仍未被证明**：`blackdetect` + `signalstats` 这条链路会真的执行，
  但冒烟测试用的 `testsrc2` 彩条素材里没有黑场，所以"能不能正确跳过片头黑场"**没有被验证过**，
  只能证明它跑得通、不报错。

## D-007 进度上报：解析 `-progress pipe:1`

**决策**：在 ffmpeg 命令里加 `-progress pipe:1 -nostats`，
由 `ProgressTracker` 解析 **stdout** 上的 `key=value` 行，以 `progress=continue` / `progress=end` 作为一次上报的结束，
换算成百分比、速度、剩余时间。

**备选方案**

- **解析 stderr 的 `time=00:01:23.45` 行**：不需要额外参数，但——
  - stderr 同时承载错误输出与日志，解析时要和错误诊断逻辑抢同一份文本，容易互相干扰；
  - 格式随 ffmpeg 版本变化（这一行是人读格式，不是稳定接口）；
  - Windows 下 stderr 的编码与换行处理更容易出问题。
- **不解析进度，只显示"运行中"**：最简单，但违反需求 7——用户不知道还要等多久。

**选择理由**

1. **`-progress` 是机器可读的稳定接口**：明确设计给程序解析，字段是 `key=value` 形式，语义固定。
2. **天然分流**：进度走 stdout、日志与错误走 stderr，两条流互不干扰
   （`process.ts` 分别提供 `onStdoutLine` 与 `onStderrLine` 回调）。
3. **字段足够丰富**：`frame` / `fps` / `out_time_us` / `speed` / `total_size` / `progress`，
   足以算出百分比、速度、剩余时间，也能把原始键值对一起传给 UI 供需要时展示。

**代价 / 权衡**

- **踩了两个格式坑，都要在代码里兜住**：
  1. `out_time_ms` 这个字段名有历史问题，**单位其实是微秒**，
     所以代码优先用 `out_time_us`（`progress.ts:110-119` 的注释与 `parseOutTime()`）。
  2. 部分硬件编码器不上报 `speed` 字段，此时只能用"已处理时长 / 已用时"反推平均速度
     （`progress.ts:82-89`），精度比 ffmpeg 自报的差。
- **需要自己做节流**：ffmpeg 默认约每 0.5 秒上报一次，但 GIF 调色板/两遍场景可能更密，
  代码里再加了一层 400 ms 节流（`progress.ts:61-66`），否则 IPC 消息会把渲染进程压住。
- **百分比在未知总时长时为 `null`**：此时 UI 退化为不确定进度条（`JobQueue.vue` 的 `progress-indeterminate`），
  这是刻意的降级而不是 bug，但意味着某些文件（如无 duration 元数据的流）永远看不到百分比。
- **裁剪时需要额外换算**：进度要相对裁剪后的区间计算，所以 `ProgressTracker` 要接收
  `trimStartSec` / `trimEndSec`（否则裁 10 秒的片段会显示 0% 停留很久）。
- **多了一层本地心跳**：因为 ffmpeg 上报有间隔，界面上的"已用时/剩余时间"如果不额外驱动就会一跳一跳的，
  所以 `JobQueue.vue` 里加了一个 1 秒的本地定时器（`tick`）。这是"为了让时间看起来在走"而加的 UI 层妥协。

## D-008 硬件编码器探测：真跑一次而不是查列表

**决策**：对每个硬件编码器（`h264_nvenc` / `hevc_nvenc` / `h264_qsv` / `hevc_qsv` / `h264_amf` / `hevc_amf`）
都**真的执行一次 0.2 秒的空转编码**——用 `lavfi` 合成 320×240、30fps、0.2 秒的黑帧，
编 6 帧后输出到 `-f null -`——根据退出码与 stderr 判定是否可用，并给出不可用的原因。

**备选方案**

- **只查 `ffmpeg -encoders` 列表**：一次调用查完所有编码器，最快。
- **查列表 + 查显卡硬件信息**（如调用 `wmic` / DXGI 枚举适配器）：仍不保证编码器能初始化成功。
- **完全信任用户选择**（让 ffmpeg 在真正转换时报错）：把问题推给用户。

**选择理由**

1. **只看列表是不可靠的**：`-encoders` 列表反映的是"这个 ffmpeg 构建**编译进了**哪些编码器"，
   而**不是"这台机器能不能用"**。列表里永远有 nvenc/qsv/amf，
   即使机器上根本没有对应显卡——用户选了"显卡加速"，转换一开始就报 `Cannot load nvcuda.dll`。
   这是"给人用"最典型的反面案例：把一个必然失败的选项摆在用户面前。
2. **真实试跑的成本极低**：`lavfi` 合成黑帧不需要读文件、不需要解码，
   320×240 编 6 帧正常 <300 ms。相比之下，让用户白等一次几分钟的失败转换代价高得多。
3. **能给出有价值的失败原因**：代码按 stderr 关键字分类——`cannot load`/`not found`/`no capable devices`
   →"未检测到对应的显卡或驱动"；`cannot open`/`device creation failed` →"显卡被占用或驱动版本过低"；
   `unknown encoder` →"当前 ffmpeg 构建未包含该编码器"；`initialize`/`error while opening encoder`
   →"编码器初始化失败（通常是驱动问题）"。这些原因直接显示在设置页。
4. **可用性会反过来影响 UI**：`useStore.ts` 的 `availableVideoCodecs` 会按探测结果把不可用的编码器置灰并说明原因，
   用户不会选到一个注定失败的选项。

**代价 / 权衡**

- **启动时要多花时间**：6 个硬件编码器**串行**试跑（刻意串行，避免同时占用多个显卡上下文互相干扰），
  最坏情况每个 15 秒超时，理论上会增加明显的启动延迟。
  **这是通过"快速探测 + 后台完整探测"两段式来缓解的**（见 D-008 相关的 `main.ts:358-374`）：
  启动时先用只查列表的快速模式让界面秒出，随后再后台完整探测并通过 `capabilities:updated` 事件刷新 UI。
- **快速模式给的是"待验证"的乐观结论**：快速模式下列表里有的编码器会先显示为可用（reason 为"待验证"），
  完整探测完成后才可能变灰。**用户在几秒的窗口期内仍可能选到不可用的编码器**——
  这个不一致是刻意的速度/准确性权衡，不是疏漏，但确实存在。
- **串行 + 超时意味着最坏情况很久**：如果驱动异常导致每次都跑到 15 秒超时，6 个就是 90 秒。
  实际只在后台发生，不阻塞界面。
- **探测结果会被缓存**：内存 + 磁盘缓存 24 小时（`capabilities.json`），
  键里包含 `ffmpegPath`，换二进制会自动失效。
  代价是**换显卡或更新驱动后最多 24 小时内仍显示旧结论**，需要用户在设置页点「重新检测」。
- **无法覆盖所有失败模式**：试跑用的是最低限度的参数（无码率控制、无 B 帧、无 look-ahead），
  某些参数组合导致的失败仍要到真正转换时才会暴露。
- **这套探测逻辑本身尚未被实机验证**：`npm run smoke` 覆盖的是 `probe.ts` / `thumbnail.ts` / `commands.ts` /
  `progress.ts` / `errors.ts`，**不包含 `capabilities.ts`**（它需要真实 GPU 与完整 Electron 环境）。
  也就是说"真跑一次而不是查列表"这个设计目前只有代码依据，没有运行记录；
  本机显卡可用性、探测耗时、24 小时缓存的实际表现都还是未知数。

## D-009 安全模型：隔离 + 白名单 + 自定义协议

**决策**：渲染进程 `contextIsolation: true`、`nodeIntegration: false`、`webSecurity: true`，
所有系统能力只通过 `preload.ts` 里显式列出的白名单方法暴露；
缩略图等本地文件通过自定义协议 `lumen-media://local/<url编码的绝对路径>` 提供，
并在 `renderer/index.html` 里用 CSP 显式允许该协议。

**备选方案**

- **关闭 `webSecurity`**：让 `<img src="file:///C:/x.jpg">` 直接可用。一行配置搞定。
- **把图片读成 base64 data URL 塞进 IPC 返回**：不需要自定义协议，也不用关 webSecurity。
- **开 `nodeIntegration`**：渲染层可以直接 `require('fs')`。
- **用 `asarUnpack` + `file://`**：仍受 webSecurity 限制。

**选择理由**

1. **关掉 `webSecurity` 是拿全局安全换一行配置**：它同时会放宽同源策略，
   让渲染进程里的任何脚本都能读取本地文件系统的内容。对一个会加载用户任意视频文件的应用来说，
   这个口子开得没有必要。
2. **自定义协议是"既有安全性又不牺牲性能"的方案**：
   - 相比 base64：不需要把整张图编码进内存再跨进程序列化，也不需要为每个文件维护一份字符串缓存；
     而且 `<img>` 能正常走浏览器缓存与流式加载（协议注册时开了 `stream: true`）。
   - 相比关 webSecurity：CSP 里精确地只放行 `lumen-media:`，其余仍然锁死为 `'self'`。
3. **统一加 `/local/` 前缀是有原因的**：Windows 盘符如果直接放在 host 位置
   （`lumen-media://c:/x.mp4`），部分 URL 解析器会把 `c:` 当成端口或协议的一部分，
   中文与空格路径也更容易踩坑。统一前缀后 `pathname` 就是一份干净的编码路径，解析逻辑只有一条分支
   （`main.ts:72-98` 的注释记录了这一点）。
4. **协议 handler 里做了存在性检查**：文件不存在返回 404、读取异常返回 500 并带上原因，
   而不是静默失败。
5. **CSP 是第二道防线**：`default-src 'self'`、`script-src 'self'`（不允许内联脚本）、
   `img-src`/`media-src` 只额外放行 `lumen-media:` 与 `blob:`。
   `connect-src` 里放行 `ws://localhost:5273` 是为了开发态 HMR。

**代价 / 权衡**

- **需要在 `app.ready` 之前注册协议**：`protocol.registerSchemesAsPrivileged()` 必须在 ready 前调用，
  这约束了主进程的初始化顺序（`main.ts:64-70`）。
- **CSP 与协议耦合**：新增任何本地资源类型（比如将来要预览音频波形）都要同时改 CSP 和协议权限，
  忘一处就是"资源加载失败但报错信息很隐晦"。
- **`sandbox: false` 是一个未收紧的点**：`main.ts:116` 里 `sandbox: false`。
  安全边界仍由 `contextIsolation` + `nodeIntegration: false` + preload 白名单保证，
  但**开启 Chromium 沙箱本可以再多一层防护**。当前设置意味着渲染进程的沙箱保护弱于 Electron 默认，
  这是一个已知的、未处理的收紧空间。
- **协议 handler 的错误信息会暴露路径存在性**：返回 404/500 的文本里带原因，本地应用场景下可接受。
- **白名单要人工维护**：`ConverterApi`（26 个方法）与 `main.ts` 的 `ipcMain.handle` 注册必须保持一致。
  目前已经出现了不一致：`settings:reset` 与 `jobs:cancel-all` 在主进程注册了但 preload 没暴露
  （见 `SESSION_SUMMARY.md` 第 5.2 节第 11 条）。

## D-010 IPC 契约集中定义在 `shared/types.ts`

**决策**：主进程、preload、渲染进程三方**共用同一份类型定义**（`shared/types.ts`），
包括数据结构、`IpcResponse<T>` 包装类型、以及 preload 暴露的 API 面 `ConverterApi` 接口。
`shared/presets.ts` 同理（容器/编码器/质量/预设目录由两侧共用）。

**备选方案**

- **各进程各自定义类型**：写起来快，但同一份数据在三处各写一遍，改一处忘一处就是运行时错误。
- **只在主进程定义、渲染层用 `any`**：丢失渲染层的类型保护，UI 层拿到的字段拼错不会被发现。
- **用 tRPC / 代码生成工具从 schema 生成类型**：对一个 26 个方法的应用来说是过度配置。

**选择理由**

1. **改一处，三处同时报错**：这是最重要的收益。比如给 `MediaJob` 加一个字段，
   渲染层如果用到了但没处理，`vue-tsc` 会直接指出。
2. **`ConverterApi` 接口即契约**：`preload.ts` 里 `const api: ConverterApi = {...}` 这一行
   保证了"暴露出去的方法签名"和"声明的契约"永远一致——**少实现一个方法会编译失败**，
   这是防止 preload 与类型定义漂移的关键设计。
3. **预设目录也需要共用**：`presets.ts` 里的容器 ↔ 编码器兼容关系（如 WebM 只接受 VP8/VP9/AV1）
   既被主进程用于参数装配与预检（`commands.ts`），也被渲染层用于过滤可选编码器（`useStore.ts`），
   **必须来自同一份数据**，否则会出现"UI 让选，但命令行装配时抛错"的不一致。
4. **两侧的类型检查配置都包含 `shared/`**：`tsconfig.json` 的 `include` 有 `shared/**/*.ts`，
   `tsconfig.electron.json` 的 `include` 也有 `shared/**/*.ts`，所以两侧都会检查这份共用代码。

**代价 / 权衡**

- **`shared/` 的改动要触发两侧重新构建**：开发态的 watch 逻辑因此要同时监听 `electron/` 与 `shared/`
  （`dev-electron.mjs:95`），改 `shared/` 会重启 Electron。
- **`shared/` 里只能放类型与纯数据**：不能放依赖 Node 或 Electron API 的实现，
  否则渲染层 bundle 会出问题。这条约束**靠注释和自觉维持**，没有工具强制
  （`shared/types.ts` 顶部写了"这里只放「数据结构」，不放实现"）。
- **`shared` 别名有两条路径**：渲染层用 `@shared/*`（Vite alias + tsconfig paths），
  主进程用相对路径 `'../shared/types'`（esbuild bundle）。
  两套引用方式并存，新增文件时要记得用对。
- **`ConverterApi` 与 `IpcEvents` 是手工维护的**：新增 IPC 通道需要同时改
  ①`shared/types.ts` ②`main.ts` 的 handler ③`preload.ts` 的实现——三处。
  虽然第 ③ 步有类型保护，第 ② 步没有（**注册了但没暴露不会报错**，这正是当前 `settings:reset` 问题的成因）。

## D-011 错误处理哲学：翻译成人话但保留原始日志

**决策**：ffmpeg 的错误先过一遍规则表（`errors.ts` 的 11 条正则，按"越具体越靠前"排序），
翻译成「一句人话结论 + 一条可操作的修复建议 + 一个分类 `kind`」，同时**完整保留 stderr 尾部原文**
（最多 40 行）作为 `rawLog`，在界面上可以折叠展开、可以选中复制。
另有「复制诊断信息」按钮，把命令行 + 完整日志 + 原始错误一并复制到剪贴板。

**备选方案**

- **直接把 ffmpeg 的 stderr 显示给用户**：实现成本为零。
  代价是用户看到的是 `[Parsed_scale_1 @ 000001] Failed to configure output pad on Parsed_scale_1`。
- **完全翻译、丢弃原始日志**：界面干净，但高级用户/评审失去自查手段，
  遇到规则表没覆盖的错误时只能看到一句"未知错误"。
- **只保留日志、不做翻译**：等于把排错工作全部推给用户。

**选择理由**

1. **需求 7 的直接要求**：项目设计目标是给人用，而错误路径恰恰是最需要"给人用"的地方——
   用户遇到失败时最需要的是"我该怎么办"。
2. **规则表覆盖的是真正高频的错误**：打不开源文件、权限不足、磁盘空间不足、编码器不可用、
   源编码装不进容器、文件损坏、时间戳异常、字幕不兼容、目标分辨率非偶数、参数不被当前版本接受。
   这些覆盖了绝大多数实际失败。
3. **保留原始日志是"不吞掉错误"的底线**：翻译层是**增量**而不是替代。
   当规则表没命中时，兜底逻辑会从 stderr 里挑出最后一行有意义的信息
   （跳过 `frame=` / `fps=` 这类纯统计行，剥掉 `[libx264 @ 0x...]` 这种无信息量的库标识前缀），
   拼成"转换失败：<那一行>"，并提示可以展开原始日志查看详情。
4. **`kind` 字段让 UI 能分类处理**：`JobError.kind` 有 7 个取值
   （`ffmpeg-missing` / `unsupported-codec` / `invalid-input` / `disk-full` / `permission` / `canceled` / `unknown`），
   界面据此决定展示方式与后续建议。

**代价 / 权衡**

- **正则规则表是脆弱的**：匹配的是 ffmpeg 的英文 stderr 文本，**ffmpeg 版本升级或措辞变化就可能失配**。
  失配不会报错，只会静默退化成"转换失败：<最后一行>"——**这是一种不会崩溃但会悄悄降级的失败模式**，
  需要靠添加真实样本的回归测试来发现（当前没有测试）。
- **规则顺序敏感**：`errors.ts` 的注释明确写了"顺序敏感：越具体的规则排在越前面"。
  这是一条**隐式约定**，新增规则时插错位置会导致更宽泛的规则抢先命中。
- **文案必须指向真实存在的入口（这里踩过一次）**：早期版本这条建议写的是"到「设置」里关闭硬件加速"，
  但 `AppSettings` 里那个 `hardwareAcceleration` 字段**从未被读取、设置页也没有这个开关**，
  **用户按提示找不到入口**。修复方式是双管齐下：把从未被读取的 `hardwareAcceleration` 与 `safeMode`
  两个字段**从类型和默认值里直接删掉**（不留"看起来能用其实是空的"配置项），
  并把文案改为指向真实存在的「**专业参数 → 视频编码器**」里改回软编码（H.264 / H.265）。
  这条经验是本决策最实际的一条：**错误提示里的每个入口都必须在界面上真的能找到**。
- **`rawLog` 只有 40 行**：`tailOf(stderr, 40)`。对长错误链可能截断关键上下文。
  同时 `process.ts` 只保留 stderr 尾部 64 KB，超长日志的早期内容会丢。
- **翻译的准确度依赖作者对 ffmpeg 的理解**：这些映射是人工编写的，没有经过大量真实错误样本的验证。

## D-012 输出文件冲突策略：自动改名

**决策**：目标文件名已存在时**自动改名**（`名称 (1).ext`、`名称 (2).ext`……最多试到 999，
再不行用时间戳），既不覆盖用户已有文件，也不直接报错。

**备选方案**

| 方案 | 问题 |
| --- | --- |
| **直接覆盖** | 用户可能丢掉已有文件，属于不可逆的数据损失 |
| **报错并要求用户改设置** | 用户要为一个命名冲突中断当前流程、回去改输出目录或文件名模板，体验差 |
| **弹窗询问"覆盖 / 跳过 / 改名"** | 批量转换时会连续弹很多次；而且批量场景下用户通常只想"都给我转出来" |

**选择理由**

1. **不丢数据是底线**：覆盖是不可逆的，代价远高于"文件名后面多个 (1)"。
2. **用户的实际意图是"我要拿到转换结果"**：绝大多数情况下用户并不关心输出叫什么，
   只关心文件在不在。自动改名让流程不中断。
3. **行为可预期**：转换完成后任务卡片上会显示完整的输出路径（`job.outputPath`），
   用户能看到实际落到哪个文件；点「打开位置」可以在资源管理器中定位。
4. **重试时也重新计算路径**：`retry()` 会带 `forceUnique = true` 重新算一次可用路径，
   避免重试时撞上自己上次的产物。

**代价 / 权衡**

- **批量转换会产生一堆带序号的文件**：连转 10 个同名源文件（比如 10 个文件夹里都叫 `video.mp4`）会得到
  `video.mp4`、`video (1).mp4`…`video (9).mp4`，用户需要自己分辨哪个是哪个。
  **缓解手段是文件名模板**（支持 `{name}` `{preset}` `{date}` `{index}`），但 `{index}` 实际不可用：
  主进程渲染模板时把它硬编码成空字符串（`convert.ts:455-460` 传 `index: ''`），
  渲染层的模板预览也**不替换** `{index}`（`DetailsPanel.vue:140-148` 只替换 name/preset/date），
  于是用户输入 `{index}` 时预览里显示字面量、实际产物里被替换成空——两边表现还不一致。
  所以这个变量目前**既没实现也没正确预览**。
- **`AppSettings` 与 `ConversionOptions` 里有 `overwrite` 字段，但主进程从不读它**：
  `useStore.ts` 里默认 `overwrite: false`，`resolveOutputPath()` 无论如何都会找不冲突的名字。
  也就是说"覆盖"这条路**既没有 UI 也没有实现**，字段是预留的。类型上看起来支持，实际不支持。
- **最多试 999 次后改用时间戳**：极端情况下（同目录同名文件超过 999 个）文件名会变成
  `名称 (1699999999999).ext`，不好看但不会失败。每次检查都是同步 `existsSync`，属于 IO 开销
  （正常情况只查 1 次）。
- **不处理"目标文件正被其他程序占用"**：改名能避开文件不存在的情况，
  但如果目标路径被占用（比如播放器打开着同名文件），仍会在 ffmpeg 阶段失败——
  不过这条会命中 `permission` 规则给出"请关闭正在占用该文件的播放器"的建议。

## D-013 渲染层目录改名 `src/` → `renderer/`

**决策**：把渲染层源码目录从 `src/` 改名为 `renderer/`，并同步更新
`vite.config.ts` 的 `root` 与 `@` 别名、`tsconfig.json` 的 `include` 与 `paths`。

**备选方案**

- **保持 `src/`**：`src/` 是前端项目的惯例命名，不必改动。
- **把主进程也挪进 `src/`**（变成 `src/main/` + `src/renderer/`）：结构更"标准"，但要动更多路径与配置。

**选择理由**

1. **消除命名不对称带来的混淆**：原结构是"主进程在 `electron/`、渲染层在 `src/`"，
   两个名字不在同一个抽象层级上——`electron/` 说的是"这是 Electron 的东西"，`src/` 说的是"这是源码"，
   而事实上主进程的源码也在 `src` 意义上。改成 `electron/` + `renderer/` 后，
   两个目录名都在回答"这段代码跑在哪个进程"。
2. **和 `shared/` 形成清晰的三分**：`electron/`（主进程）、`renderer/`（渲染进程）、`shared/`（共用），
   新成员看一眼就知道代码该放哪。
3. **改动成本很低**：只有 3 个配置点（Vite `root`/alias、两个 tsconfig），
   源码内部的 import 用的是 `@/` 别名与 `@shared/` 别名，**不依赖目录名**，所以源码零改动。

**代价 / 权衡**

- **历史文档与外部引用会失效**：任何已经写好的、指向 `src/App.vue` 的说明都要更新
  （本次交付的文档统一使用 `renderer/`）。
- **`@` 别名的语义变了**：`@/*` 现在映射到 `renderer/*`。
  这在 `vite.config.ts` 与 `tsconfig.json` 里各配置了一份，**两处必须保持一致**，
  否则会出现"编辑器不报错但构建失败"或反之。
- **属于非功能性改动，没有带来任何功能收益**：纯粹是可读性投资，在限时任务里花时间做重构是有风险的
  （本次改动发生在功能开发基本完成之后，风险可控）。

## D-014 打包时二进制的释放方式：`extraResources`

**决策**：在 `package.json` 的 `build.extraResources` 里把 `resources/bin/ffmpeg.exe` 与
`resources/bin/ffprobe.exe` 释放到安装目录的 `resources/bin/`；应用代码在打包态通过
`process.resourcesPath` 定位这两个文件。**不依赖 `asarUnpack`。**

**备选方案**

- **`asarUnpack: ["**/*.exe"]`**：把 asar 里的 exe 解出来，理论上也能执行。
- **把二进制放在 `files` 里一起打进 asar**：**不可行**——asar 是归档格式，里面的 `.exe` 无法被执行。
- **让用户自己下载 ffmpeg**：违反需求 7。

**选择理由**

1. **asar 内的 `.exe` 无法执行**，这是硬性限制，所以二进制必须落在 asar 之外。
2. **`extraResources` 的路径可预测且稳定**：`process.resourcesPath` 在打包态就是 `<安装目录>/resources`，
   拼上 `bin/ffmpeg.exe` 即可，不涉及 asar 路径重写。
   `binaries.ts:11-12` 的注释明确写了"这里刻意不走 asarUnpack 路径，避免 `__dirname` 被替换成 `app.asar` 的问题"。
3. **开发态与打包态可以用同一套目录约定**：
   - 开发态：`<项目根>/resources/bin/ffmpeg.exe`（`app.getAppPath()` 是项目根）
   - 打包态：`<安装目录>/resources/bin/ffmpeg.exe`（`process.resourcesPath`）
   代码里把两个候选都放进查找列表（`binaries.ts:39-75`），**同一份 `resources/bin/` 布局在两种形态下都成立**，
   `fetch-binaries.mjs` 也只需要往一个地方写。
   注意 `package.json` 里仍然保留了 `asarUnpack: ["**/*.exe"]`，但主查找路径并不依赖它。
4. **`extraResources` 是显式白名单**：只有列出的两个文件会被释放，
   不会因为 `files` 的 glob 写宽了而把无关内容带进安装包。

**代价 / 权衡**

- **二进制候选路径现在只有 2 个**：`binaries.ts` 的 `bundledCandidates()` 依次尝试
  `process.resourcesPath/bin/<kind>.exe`（打包态）与 `app.getAppPath()/resources/bin/<kind>.exe`（开发态）。
  早期版本还包含 `node_modules/ffmpeg-static/ffmpeg.exe`、`node_modules/ffprobe-static/bin/<平台>/<架构>/ffprobe.exe`
  两个兜底候选，**随 D-004 改用自管二进制而一并删除**——所以那两份路径现在是死引用，不应再出现在文档里。
  最终用了哪一个由设置页诊断区显示（`ResolvedBinary.source` 记录
  `custom` / `bundled` / `system` / `missing`）。
- **二进制约 278 MB 会进安装包**：`ffmpeg.exe` 139.1 MB + `ffprobe.exe` 138.9 MB，
  安装包体积因此显著增大，且 `extraResources` 是**不做压缩优化**的（直接释放文件）。
- **只有 Windows 路径被真正验证过**：`EXE` 常量按平台拼 `.exe`，
  但打包配置只有 `win: nsis x64`，**非 Windows 路径属于未验证代码**。
- **安装包形态尚未验证，便携版形态已验证**：NSIS 安装包在本机受限网络下做不出来（原因见 D-017），
  所以"extraResources 在**安装后**确实能释放出可执行的 ffmpeg"仍只是配置与代码层面的推断；
  但 `release/Lumen-conv-便携版/resources/bin/` 这个**相同布局**已经实机跑通
  （便携版自检 68/68 通过、退出码 0，见 `docs/SESSION_SUMMARY.md` 第 4.1.1 节）。

## D-015 应用图标用脚本生成，而不是放一张现成图片

**决策**：新增 `scripts/make-icon.mjs`，用 **ffmpeg 的 `geq` 滤镜逐像素计算**出图标图形
（深色圆角底 `#15181f` + 琥珀色播放三角 `#f0a03c`，与界面强调色一致），
输出 `build/icon.png` 与 `build/icon.ico`（内嵌 16/24/32/48/64/128/256 共 7 档 PNG）。
脚本**内置像素自检**（`verifyPng()`），自检不过就以非 0 退出码失败。

**备选方案**

| 方案 | 说明 | 为什么不选 |
| --- | --- | --- |
| **放一张现成的 PNG/ICO 图片** | 最直接，`electron-builder` 的 `win.icon` 指过去就行 | 需要把二进制素材入库；且素材来源要么是网上找的（许可不明），要么是手工做的（不可复现、改一次要重做） |
| **引入 `sharp` + `png-to-ico`** | 用成熟的图像库画图与打包 ICO | 为一张图标引入两个原生依赖（`sharp` 还带平台二进制），与"少一层依赖"的整体取向冲突 |
| **用 SVG + 转换工具** | 矢量、可缩放 | 仍然要引入渲染/转换工具链；而且 Windows 的 `.ico` 最终仍要位图多尺寸打包 |
| **`ffmpeg drawtext` 画 `▶` 字符** | 看起来最省事，一行滤镜 | **实际踩坑（第一版）**：这份 ffmpeg 构建不解析 `\u25B6` 转义，图标上出现了**字面的 "25B"** |

**选择理由**

1. **零新增依赖**：只用项目已经必须携带的 `resources/bin/ffmpeg.exe`，
   任何装了 ffmpeg 的机器都能复现同一张图，不需要额外的图像库或素材文件。
2. **可复现、可 diff**：图形是源码里的一段表达式（顶点坐标、圆角半径、两个颜色常量），
   改了就能重新生成，不会有"这张图是谁怎么做的"的问题。
3. **ICO 容器自己拼就够了**：Vista 之后的 `.ico` 允许直接内嵌 PNG（而不是 BMP + 掩码），
   所以只要写 6 字节头 + 每档 16 字节目录项 + 各档 PNG 数据即可，**不值得为此引一个依赖**。

**代价 / 权衡**

- **踩了两次"脚本报成功但图是错的"**，这是本决策最值得记录的部分：

  | 版本 | 做法 | 实际结果 | 为什么没被发现 |
  | --- | --- | --- | --- |
  | 第一版 | `drawtext` 画 `▶`（`\u25B6`） | 该构建不解析 `\u` 转义，图标上画出**字面 "25B"** | 脚本只看 ffmpeg 退出码，退出码 0 就认为成功 |
  | 第二版 | 改用 `geq` 逐像素算三角 | 三个半平面的**方向写反**，交集变成并集，图标成了"**蝴蝶结**" | 同上：脚本依然"成功"，而且 `.ico` 文件大小、尺寸都正常 |

  教训：**"命令成功"和"结果正确"是两件事**（这一点在本项目的 GIF 滤镜链 bug、
  界面自检截到空白设置页上也各出现了一次）。所以第三版在脚本里加了 `verifyPng()`。

- **像素自检是启发式的，但足以拦住这两类错误**：把生成的 PNG 用 ffmpeg 的
  `crop=1:1:…,format=rgb24` 解出两个像素，断言**中心必须是琥珀色**
  （`r>180 && g>110 && b<110`，即三角内部）与**右上角必须是深色底**（`r<60 && g<60 && b<70`）。
  "蝴蝶结"版本会让中心像素不是琥珀色，"25B"版本会让中心像素落在字符笔画之外——两种都能拦住。
  自检只在 256px 档执行（小尺寸的抗锯齿会让阈值判断不稳）。
- **`geq` 表达式可读性差**：圆角遮罩是四个象限的 `hypot()` 判断相加，三角是三个 `gte/lte` 相乘，
  调试只能靠改数看结果。因此脚本头部用注释把顶点坐标与半平面推导写清楚了
  （`A(0.33W,0.26H)`、`B(0.33W,0.74H)`、`C(0.72W,0.5H)`，斜率 `k≈0.6154`），
  并把两次踩坑记录进注释，避免后来者重蹈。
- **必须 4× 超采样**：`geq` 是硬阈值判断，直接按目标尺寸算会让三角边缘呈锯齿状
  （小尺寸图标尤其明显）。脚本先在 `size × 4` 上计算再 `scale=size:size:flags=lanczos` 降采样。
- **脚本没有接进 `npm run build`**：图标是"改一次用很久"的资源，没必要每次构建都重算。
  需要时手动执行 `npm run make:icon`（依赖 `resources/bin/ffmpeg.exe`，所以要先 `npm run setup`）。
- **产物入库，脚本也入库**：`build/icon.ico` 与 `build/icon.png` 已生成并提交
  （合计不到 10 KB），这样打包不依赖"先跑一次图标脚本"；同时脚本保留，便于以后调整配色或加尺寸。
- **图标已就绪，但当前唯一已产出的打包形态用不上它**：`scripts/package-portable.mjs` 会尝试用 `rcedit.exe`
  把 `build/icon.ico` 写进便携版的 exe，但该版本 rcedit 在含非 ASCII 字符的路径下会失败（本项目路径含中文），
  于是便携版 exe 仍是 Electron 默认图标、版本信息也是 Electron 原值（详见 D-017）。
  本机没有产出过带图标的安装包。

## D-016 跨进程传参统一走去响应式的纯对象

**决策**：渲染进程向主进程发送的任何结构化数据（当前主要是 `CreateJobRequest[]` 里的 `ConversionOptions`），
都必须先**脱离 Vue 响应式**，以纯对象形式交给 `ipcRenderer.invoke`。
统一做法是 JSON 往返：

```ts
// renderer/composables/useStore.ts
export function effectiveOptions(file: LoadedFile): ConversionOptions {
  const merged = { ...options.value, ...(file.overrides ?? {}) };
  return JSON.parse(JSON.stringify(merged)) as ConversionOptions;
}
```

**背景（这是一个已发生的真实缺陷，不是假想）**：这条决策是被一条让核心功能不可用的缺陷逼出来的。
合并全局选项与文件级 `overrides` 时用展开运算符，**从响应式对象上读出的数组字段是 Proxy 数组**；
`ipcRenderer.invoke` 用结构化克隆（structuredClone 语义）序列化参数，Proxy 不可克隆，
于是抛 `An object could not be cloned.`，`startConversion()` 的 Promise 无人兜住，
用户点「开始转换」**什么都不发生**。

触发条件比最初以为的更宽：不只"改过字幕勾选"，而是**任何一次转换点击**——因为 `options` 这个 `ref`
自身的 `subtitleStreamIndexes` / `audioStreamIndexes` 就已经是 Proxy 数组（可用
`node -e "const {ref,isProxy}=require('vue');const o=ref({a:[]});console.log(isProxy({...o.value}.a))"`
一类的最小实验复现，详见 `docs/SESSION_SUMMARY.md` 第 5.1.1 节）。

**备选方案**

| 方案 | 说明 | 为什么不选 |
| --- | --- | --- |
| **直接把响应式对象传给 IPC** | 代码最短（即修复前的写法） | **就是缺陷本身**。Proxy 不满足结构化克隆的类型要求，必抛 `An object could not be cloned.` |
| **在主进程侧 `toRaw()`** | 收到参数后解包 | **时序上不可能**：克隆发生在渲染进程发送的那一刻，主进程拿到手之前就已经抛错了，根本没有"收到参数"这一步。而且 `toRaw()` 只解一层，合并结果里的嵌套数组仍是 Proxy |
| **渲染进程用 `structuredClone()` 手动深拷贝** | 看起来最"正统" | 它和 IPC 用同一套序列化算法，**遇到 Proxy 一样抛 `could not be cloned`**（错误信息还完全相同，容易误判成"IPC 的问题"）。要让它工作必须先逐层 `toRaw()` 解包，既啰嗦又容易漏 |
| **手写递归解包 / 引入 `klona`、`rfdc` 之类的深拷贝库** | 通用，能保留 Date / Map | 为一个 14 字段的扁平结构引依赖、写递归，收益与成本不匹配；本项目整体取向是"能不加依赖就不加"（`dependencies` 至今为空对象） |
| **JSON 往返（`JSON.parse(JSON.stringify(x))`）** | 一行搞定，且天然只保留可克隆类型 | **选中**。它同时完成两件事：深度解包响应式、得到一个绝对可克隆的普通对象 |

**选择理由**

1. **它解决的是"类型"问题，而不只是"这次的值"问题**：JSON 往返之后，无论上游怎么加字段、
   怎么嵌套，送给 IPC 的都是同一类普通对象——**不会因为以后某个字段变成数组/对象就重新踩坑**。
2. **当前结构正好落在 JSON 的能力范围内**：`ConversionOptions` 的 14 个字段只有
   `string` / `number` / `boolean` / `null` 与 `number[]` 这几种形态（见 `shared/types.ts`），
   JSON 往返是无损的。
3. **错误的传播方式已验证**：修复后 `npm run smoke:ui:full` **68/68 通过、退出码 0**，
   控制台不再出现任何 `An object could not be cloned.`；同时 `startConversion()` 补了
   `try/catch` + `showToast('无法创建转换任务：' + msg, 'danger', 8000)`，
   这类错误以后不会再静默。

**代价 / 权衡**

- **会丢失 JSON 表达不了的类型**：`Date` 会变成 ISO 字符串、`Map`/`Set` 会变成 `{}`、
  `undefined` 字段会被整个丢弃、`NaN`/`Infinity` 会变成 `null`、函数会消失。
  **当前 `ConversionOptions` 里没有这类值**，所以可接受；但这是一条明确的边界——
  如果将来要跨 IPC 传 `Date`（例如任务时间戳）或 `Map`，**不能再套用这个写法**，
  应当改用显式的序列化（时间戳传 number、Map 转数组）或引入深拷贝方案。
- **多一次序列化开销**：对 14 个字段的对象可以忽略；不应把这个写法用到大体量数据上
  （例如整份探测结果或日志数组），那种场景应当只传必要字段。
- **`as ConversionOptions` 是类型断言，不是校验**：JSON 往返不检查字段是否齐全。
  `JSON.stringify` 丢掉 `undefined` 字段时类型系统不会报错，所以**新增字段必须给 `null` 默认值而不是留 `undefined`**。
- **它只解决"传得过去"，不解决"传对了没有"**：参数正确性依然要靠冒烟测试与界面自检断言
  （这也是为什么本轮同时强化了"按钮点击真的创建了任务"这条断言，见 `docs/SESSION_SUMMARY.md` 第 5.1.1 节）。
- **纪律需要人来守**：目前靠注释与这条决策记录约束，**没有 lint 规则或类型层面的强制**
  （例如禁止把 `Ref`/`reactive` 对象直接喂给 `window.converter.*`）。如果这类调用点继续增多，
  应当考虑加一条 ESLint 规则或把 `preload` 的入参类型收紧为 `DeepReadonly<Plain>` 之类的纯数据类型。

## D-017 打包方式（受限网络）：离线手工组装便携版，而不是继续调 electron-builder

**决策**：新增 `scripts/package-portable.mjs`，**完全离线手工组装** Windows 便携版
（`npm run dist:portable` = `node scripts/package-portable.mjs --build`），产物为
`release/Lumen-conv-便携版/`（`Lumen-conv.exe` 200.4 MB，目录总计 602.3 MB）。
**放弃在本机用 `electron-builder --win nsis` 产出 NSIS 安装包**，但**保留 `package.json` 里完整的
electron-builder 配置**与 `npm run dist:nsis` 入口，供有网络的环境使用。

**背景（这不是设计取舍，是环境限制）**：`electron-builder --win nsis` 在本机**两次实测都卡在同一处**，
以 `Timeout awaiting 'request' for 600000ms` 失败（10 分钟等待后超时）。两个原因：

1. 它需要**额外的工具链**（`app-builder-bin`、`nsis`、`winCodeSign`），这些都要在打包时按需获取，受限网络下必然超时；
2. 它使用的 **Electron 二进制缓存与 `@electron/get` 不通用**——`scripts/fetch-binaries.mjs --electron`
   已经下载好的那份运行时它不认，所以"本地已经有 zip"也帮不上忙，它仍要重新下载。

**备选方案**

| 方案 | 说明 | 代价 / 为什么不选 |
| --- | --- | --- |
| **继续调 electron-builder（换镜像、加代理、预置缓存）** | 给 `ELECTRON_BUILDER_BINARIES_MIRROR` 等环境变量指向国内镜像，或手工把 `nsis` / `winCodeSign` 预置进缓存 | ① 瓶颈不只是"下载慢"：工具链要现取，且 Electron 缓存**不通用**这一条不是换个源能解决的；② 安装包**不是本轮的验收前提**（需求 2 要的是"能真的转码"），继续调它是在与一个不可控的外部依赖搏斗；③ 失败模式是 10 分钟超时，迭代一次的成本极高 |
| **改用 `@electron/packager`** | 它复用 `@electron/get` 的缓存（也就是本机已经有的那份运行时），只用 `electron` 这一个依赖 | 仍然要**新装一个依赖**，而它同样不是零风险：它会自己去解析/校验 Electron 缓存，受限网络下仍可能卡；而且它给的是"解包目录"，要出单文件安装包还是得再配一套打包器。引入新依赖与本项目"能不加就不加（`dependencies` 至今为空对象）"的取向冲突 |
| **手工组装（选中）**：复制运行时 + `@electron/asar` 打包 + 复制 ffmpeg + rcedit 写信息 + rename 收尾 | 逻辑很短、完全可复现、**不触发任何下载**；`@electron/asar` 与 `electron-winstaller`（提供 `rcedit.exe`）本来就已随 `electron-builder` 装在 `node_modules` 里，**不需要新增任何依赖** | 见下方"代价"，主要代价是**失去了 electron-builder 生态的全部配套** |
| **不打包，只交付源码 + `npm run setup`** | 最省事 | 便携版的价值恰恰是"评审不需要自己构建"——clone 后必须联网抓 290 MB 二进制这一步会被直接卡住。已实测的便携版解决了这个问题 |

**选择理由**

1. **离线可复现是硬需求**：本机网络的不可控点已经出现过多次（npm 缓存 EPERM、Electron postinstall 卡住、
   GitHub 直连不通），打包这一步不能再依赖网络。手工组装只用**磁盘上已有的东西**：
   `node_modules/electron/dist`、`dist/`、`dist-electron/`、`resources/bin/`。
2. **逻辑短到可以自己维护**：整个脚本 5 个步骤，没有隐藏的模板与中间产物，
   出错时行为可预期（例如 rename 被占用就回退为复制，见下）。
3. **产物形态正好与代码约定一致**：`resources/bin/ffmpeg.exe` 这个位置**同时满足开发态与打包态的查找路径**
   （`binaries.ts` 的 `bundledCandidates()`），因此 `binaries.ts` **一行都不用改**（见 D-014）。
4. **实测有效**：便携版实跑
   `--smoke --smoke-file=… --smoke-assets=<仓库 test-assets 目录> --smoke-convert`
   **68/68 通过、退出码 0**（含应用内真实转换：`done`、产物 3.15 MB、进度 100%）。
   > `--smoke-assets` 是后补的：打包态 exe 旁边没有测试素材，不给这个参数会有 8 项多文件检查
   > 被静默跳过（摘要照样打印"全部通过"）。现在会**明确报一条失败**，见 `SESSION_SUMMARY.md`
   > 第 5.1 节第 14 条。

**代价 / 权衡（必须写清楚）**

- **要自己维护 app.asar 的布局**：进 asar 的 `package.json` 是脚本手写的精简版
  （只保留 `name` / `productName` / `version` / `description` / `author` / `license` / `main`），
  且要手动排除 `default_app.asar`。Electron 的目录结构或 asar 约定一旦变化，得自己跟进。
- **失去 electron-builder 生态的全部配套**：**NSIS 安装向导**、**自动更新**（`electron-updater` 那套）、
  **代码签名**、多平台目标、以及"图标与版本信息由工具链自动写入"这条链路。
  便携版只覆盖了"解包后能运行"这一种形态。
- **当前便携版的 exe 是 Electron 默认图标，且没有版本信息**：脚本会调
  `node_modules/electron-winstaller/vendor/rcedit.exe` 写图标与版本信息，但该版本 rcedit 在
  **路径含非 ASCII 字符**时（本项目路径含中文）报 `Fatal error: Unable to load file`，脚本如实跳过。
  实测 `Lumen-conv.exe` 的版本信息仍是 Electron 原值（`ProductName=Electron`、`OriginalFilename=electron.exe`）。
  **脚本刻意不做环境相关绕行**（例如把 exe 复制到临时 ASCII 路径再改回来）——
  那会让构建脚本依赖具体环境，反而更难维护；图标缺失不影响功能。
- **前提是"已经装好依赖与二进制"**：脚本开头会检查 `node_modules/electron/dist/electron.exe` 与
  `resources/bin/{ffmpeg,ffprobe}.exe`，缺失就直接失败并提示先跑 `npm run setup`。
  所以"离线"指的是**打包过程**不联网，不是"从零开始、什么都不用下"。
- **只有 Windows 路径被验证过**：脚本里写死了 `electron.exe`、`APP_NAME.exe`、`resources/bin/*.exe`，
  没有做平台分支，非 Windows 环境属于未验证代码。
- **没有把 `dist` 脚本改掉**：`npm run dist` 仍是 `npm run build && electron-builder --win`（原样保留），
  新增的 `dist:nsis` 是它的显式 NSIS 版本；`dist:portable` 则指向新的离线脚本。
  这样命名上有个需要记住的点：**`dist:portable` 不经过 electron-builder**，
  而 `package.json` 的 `build.portable` 字段（`${productName}-${version}-portable.exe`）目前**无人使用**，
  留作有网络环境时的备选。

**这条决策的适用边界**：它是"**在受限网络、只有 Windows、三天工期**"这三个约束下的最优解，
不是"手工组装比 electron-builder 更好"。一旦有稳定网络，`npm run dist:nsis`
（带图标、带版本信息、带安装向导的正式安装包）应当是首选。

## D-018 「推荐 / 自定义」两种模式的差别必须落在**首屏**，不能只藏在折叠线下

**背景（用户反馈，原话）**

> "推荐设置和自定义没区别啊"

这条反馈来自用户真的切到「自定义」之后。当时的实现**在代码上确实分了两种模式**：
`appMode === 'custom'` 时多出一个专业参数区块、质量区里多一个帧率下拉。
但用户说"没区别"——因为**这些差别全在折叠线以下**。

**量化根因（不是靠读代码猜的，是量出来的）**

自检脚本把两种模式"视口内的区块"打印出来，得到：

| 模式 | 首屏可见区块（改动前） |
| --- | --- |
| 推荐 | 视频信息@106 → 用途@376 → 在哪播@787 → 质量与尺寸（折叠线下） |
| 自定义 | 与推荐**逐块相同**（专业参数在 900px 之外，首屏看不到） |

两个原因叠加：

1. **「视频信息」默认展开**——8 行明细占了约 270px，把「用途」推到 376px，
   「在哪播 / 多大体积」推到 787px（视口高度约 800px，正好压线）。
2. **专业参数区块挂在面板末尾**——约 900px 处，首屏根本看不到。

所以用户的第一屏在两种模式下**几乎逐像素相同**，说"没区别"是完全准确的。

**决策**

1. 「视频信息」默认**收起**成一行摘要（`时长 · 体积 · 分辨率 · 容器 · 编码`），
   需要细节再展开；折叠态由 `infoOpen` 控制（默认 `false`）。
2. 模式切换正下方加一行**当前方案摘要**（`plan-summary`：用途 + 参数摘要），
   让"这套参数会怎么转"不用滚动就能看到，切换模式时这一行立刻变化。
3. 专业参数区块（改名「**专业参数**」，原来是"高级选项"）整体**搬到面板最上面**，
   仅自定义模式出现——它成为首屏第一个区块，两种模式的差别一眼可见。
4. 切到自定义模式**不再自动展开**专业参数（原实现是 `advancedOpen.value = true`，
   理由是"省一次点击"）。

**为什么第 4 条要反着改（这是本次唯一"变差一点"的取舍）**

自动展开在"专业参数位于面板末尾"时是无害的——页面只是变长。
搬到最上面之后，自动展开的后果变成：一进自定义模式，**首屏全是待填的专业字段**，
而「用途 / 在哪播 / 质量」被推到 1000px 之外，用户失去参照物。

改成默认收起后，自定义模式首屏是：`专业参数（收起，一行）→ 视频信息摘要 → 用途 → 在哪播 / 多大体积`，
和推荐模式**保留了同样的信息骨架**，差别是顶部多了一行专业参数入口。
代价是专业用户要多点一次，换回来一个有上下文的界面——这个交换是划算的。

**验证（可复现）**

```
npm run smoke:ui:file        # 56/56 通过，退出码 0
npm run smoke:ui:full        # 68/68 通过，退出码 0
```

自检里新增/强化的断言，把"看不出区别"这件事变成可判定的：

| 断言 | 实测输出 |
| --- | --- |
| 两种模式在首屏（折叠线以上）就有可见差别 | 推荐首屏：`视频信息@152 / 你要拿去干什么@235 / 在哪播 / 多大体积@646`<br>自定义首屏：`专业参数@152 / 视频信息@205 / 你要拿去干什么@288 / 在哪播 / 多大体积@699` |
| 自定义模式：专业参数面板出现在首屏（不用滚动就能看到） | `专业参数@152`。注：D-019 之后这条断言改名为「专业参数**面板**」，判定依据也从折叠开关换成了 `.pro-block` |
| 推荐模式：首屏能看到"用途"与"在哪播 / 多大体积" | 通过（推荐模式仍是原来的骨架） |

> 这条断言本身也修过一次：原来只打印**推荐模式**的首屏，靠一个字符串比较判定"有差别"——
> 等于让断言自己证明自己，日志里看不到自定义模式首屏到底长什么样。
> 现在两种模式的首屏都打印出来，证据可以直接被人读。

**本次改动里踩到的坑（值得记下来）**

把专业参数区块"搬到最上面"时，第一版只搬了**开标签**（`<section>` + `<div class="advanced-body">`），
没搬内容，还多留了一个 `</div>`，于是 `pro-block` 把「视频信息 / 用途 / 在哪播 / 质量」全包了进去。
后果很严重：推荐模式下这些区块会被 `v-if="appMode === 'custom'"` 一起隐藏掉。
`vite build` 直接报 `Element is missing end tag`，`vue-tsc` 也过不了——**构建期就拦住了**。
教训：搬动模板片段时，"开标签 / 内容 / 闭标签"必须作为整体移动，改完立刻跑一次 `vite build`。

**代价 / 权衡**

- 自定义模式首屏比推荐模式多一行（约 53px），其余区块整体下移同样距离；
  「质量与尺寸」因此在自定义模式下更靠下——但「用途」「在哪播」仍在首屏内。
- 专业用户从"切过去就看到全部字段"变成"切过去看到入口，再点一下"。
- 两种模式的**参数本身没有区别**（用途、在哪播、质量、分辨率在两边都能改），
  区别只在"专业参数是否可见"和"帧率是否可见"。这是设计如此：
  自定义模式不是另一套引擎，而是**把同一套参数的隐藏项摊开**。

> ⚠ **本决策的第 3、4 条已被 D-019 取代**：用户在看到成品后明确要求
> "自定义不要这个推荐，缺少专业性，这个用最初那个版本自己调整更合适"。
> 最终形态是——自定义模式下专业参数**常开**（不再有折叠入口），
> 用途推荐卡片**整块不渲染**。D-018 保留下来的有效部分只有第 1、2 条
> （视频信息默认收起、新增方案摘要）和"模式差异必须落在首屏"这个原则本身。

## D-019 自定义模式不做推荐：用途卡片只属于推荐模式，专业参数常开

**背景（用户反馈，原话）**

用户在看完成品、并实际操作之后提出：

> "自定义不要这个推荐，缺少专业性，这个用最初那个版本自己调整更合适"

（配图是「你要拿去干什么」那 8 张用途卡片 + "选一个用途就够了，细节我来定"那行提示。）

D-018 解决的是"两种模式**看不出**区别"，手段是把专业参数入口搬到首屏。
但用户的下一层意思是：自定义模式里**根本不该出现推荐卡片**——
既然我自己会调，就别再给我摆一排"选一个就够了"。

**决策**

自定义模式下：

1. 「你要拿去干什么」整块**不渲染**（`v-if="appMode === 'recommended'"`），
   连同它的"用途说明"、"参数已偏离推荐值"提示、用途小贴士一起。
   理由：这些内容讲的都是**推荐值**，在一个"我不需要推荐"的语境里只会制造噪音。
2. 专业参数**常开**：删掉原来的「专业参数 ▸」折叠开关与 `advancedOpen` 状态，
   改成标题 + 直接铺开的字段区（`<header class="block-head"><h4>专业参数</h4></header>` + `.advanced-body`）。
3. 参数摘要行在自定义模式下显示「**自定义参数**」而不是用途名——
   用途卡片都看不见了，再写一个用户改不了的用途名只会让人困惑。
4. **兼容性预检单独拆成一个区块，两种模式都显示**。
   它是唯一一个"必须活下来"的部分：自定义模式下用户更容易手选 H.265 给老电视，
   而这条警告讲的是事实（那台设备解不了），不是推荐。
5. 区块顺序靠 CSS `order` 调整（不复制模板）：
   `专业参数 → 质量与尺寸 → 在哪播 / 多大体积 → 视频信息 → 兼容性预检`，
   即"要调的参数按调整顺序排前面，参考信息与检查结果放后面"。

**参数继承问题（必须说清楚）**

隐藏用途卡片**不会**清空参数：切到自定义模式时，格式 / 编码 / 分辨率 / 体积上限
仍是上一次用途留下的值（默认是「发微信 / QQ」，即 MP4 + H.264 + ≤100 MB）。
这是刻意的——切个模式就悄悄改掉用户的参数更糟。
这些值在专业参数区（格式 / 编码器）与「质量与尺寸 / 哪播多大体积」里都看得见、改得动，
摘要行也把它们列出来了。

**验证（可复现）**

```
npm run smoke:ui:file    # 56/56 通过，退出码 0
npm run smoke:ui:full    # 68/68 通过，退出码 0
```

新增两条专门盯这次需求的断言：

| 断言 | 实测输出 |
| --- | --- |
| 自定义模式：不出现「用途」推荐卡片（用户明确要求） | 自定义模式下用途卡片数 = **0** |
| 推荐模式：用途推荐卡片齐全 | 推荐模式下用途卡片数 = **8** |
| 自定义模式：出现专业参数（且字段直接可见，不需要再点一次） | 专业参数区块与字段都在 |

首屏对照（自检打印的实测值）：

```
推荐首屏：视频信息@152 | 你要拿去干什么@235 | 兼容性预检@553 | 在哪播 / 多大体积@696
自定义首屏：专业参数@152
```

自定义模式首屏就是参数本身——专业参数面板占满一屏，这正是"最初那个版本自己调整"的形态。

**代价 / 权衡**

- **自定义模式的首屏没有"视频信息"了**（它被排到参数之后）。专业用户切过去先看到
  要调的字段，而不是文件信息；想核对源参数得往下滚一点。这是"参数优先"的直接代价。
- **推荐模式的偏离提示在自定义模式不可见**：用户在自定义模式把参数改得和用途推荐值不同时，
  不会再看到"已偏离"的提示。信息没有丢（参数就在眼前），但**少了一层提醒**。
  恢复途径是切回推荐模式。
- **字段更多、页面更长**：自定义模式内容高度从约 1266px（折叠态）变成更长，
  但这就是专业模式该有的样子。
- 兼容性预检被拆出来单独成块，推荐模式下它多了一行标题（约 25px）。

**这次踩到的坑（值得记下来）**

`evalJs` 的表达式是**模板字面量**，我在里面加注释时写了反引号包住的 `.usecase-card.active`，
反引号提前结束了模板串，后面的内容被当成 JS 表达式解析，编译出的代码里凭空多出一个
未定义的 `card` 标识符——自检直接 `ReferenceError: card is not defined`，整个自检中断。
**规则：`evalJs` 的表达式字符串里（包括注释）绝不出现反引号。**
